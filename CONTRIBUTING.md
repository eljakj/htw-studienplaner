# Contributing

Small steps, one issue at a time. Every change starts as a GitHub issue and ends as one pull request.

## Workflow

1. Pick one issue and read its acceptance criteria. Open questions are answered before coding starts.
2. Create a branch named `type/short-description`, for example `chore/repo-skeleton` or `feat/export-json`.
3. Commit with [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`.
4. Open a pull request that contains `Closes #<issue number>`. One issue, one pull request.
5. Merge only when all checks are green (see [Continuous integration](#continuous-integration)).

## Definition of Done

- Tests are green.
- README and docs are up to date.
- No personal data in the repository: no profiles, exports, screenshots or logs with real study data.

## Language

Code, commits, issues and pull requests are in English. The user interface is in German. The README is in German with a short English summary.

## Personal data

`profile.json`, `*.profile.json` and `studienverlauf-*.json` are git-ignored. The build has no option for personal data; your own plan lives in the browser and in your export file. The example plan lives in `demo/` and must be fictional. If personal data was committed by mistake, tell the maintainer before pushing; removing it from the history is a separate, careful step.

## Setup

You need Python 3 and Git. On Windows use Git Bash or WSL2; on Linux and macOS use any shell.

Create a virtual environment and install the dev dependencies:

```bash
python -m venv .venv
source .venv/bin/activate        # Linux, macOS, WSL2
source .venv/Scripts/activate    # Git Bash on Windows
pip install -r requirements-dev.txt
```

In PowerShell, activate with `.venv\Scripts\Activate.ps1`.

Install the test browser once (about 150 MB):

```bash
python -m playwright install chromium
```

## Build

```bash
python build.py
```

This writes `dist/index.html`, one self-contained file. Open it in a browser. `dist/` is git-ignored. The build is always neutral; there is no profile option.

## Run the tests

```bash
python -m pytest
```

This runs the unit tests in `tests/unit`. `pytest.ini` puts `src/` and the repository root on the import path. The tests for `src/semester.js` and `src/exchange.js` run the JavaScript in headless Chromium (they need the browser from the step above) and pass the date in, so they do not depend on today's date.

The browser tests in `tests/e2e` build the page, serve it on a free local port and open it in Chromium. They run separately:

```bash
python -m pytest tests/e2e
python -m pytest tests/e2e --headed    # watch the browser
```

Each test gets a fresh browser context, so no state is shared. A test fails on JavaScript errors and on any request that leaves the local server. After a failure, `test-results/` contains a trace; open it with `python -m playwright show-trace <path>/trace.zip`.


## Docker

```bash
docker build -t htw-studienplaner .
docker run --rm -p 8080:8080 htw-studienplaner
```

Then open http://localhost:8080. The image contains only the neutral build and runs nginx as a non-root user. `/healthz` is the health endpoint. The browser tests can run against the container:

```bash
E2E_BASE_URL=http://127.0.0.1:8080 python -m pytest tests/e2e    # Git Bash, Linux, macOS
$env:E2E_BASE_URL="http://127.0.0.1:8080"; python -m pytest tests/e2e    # PowerShell
```

The Content Security Policy is generated by `build.py` (see ADR-0003).

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request and on every push to `main`: a guard against tracked personal data, unit tests, build, E2E tests. The built page (and, after a failure, the Playwright traces) is kept as an artifact for 7 days: Actions tab, open the run, section "Artifacts".

### Branch protection (one-time setup in the GitHub settings)

Settings, Rules, Rulesets, New branch ruleset: target `main`, enable "Require a pull request before merging" (0 required approvals, because a solo maintainer cannot approve their own pull request), "Require status checks to pass" with the check `test`, and "Block force pushes". The check `test` can only be selected after the workflow has run once.

## Container image (GHCR)

After CI succeeds on `main`, `.github/workflows/release-image.yml` builds and pushes `ghcr.io/eljakj/htw-studienplaner` with the tags `sha-<7 characters of the commit>` and `latest`. A version tag (`git tag v1.0.0 && git push origin v1.0.0`) additionally publishes `1.0.0`, `1.0` and `1`; it only works for commits whose CI run was green. The tag rules are in `scripts/image_tags.py`.

The first push creates the package as private. Set it to public once: GitHub profile, Packages, `htw-studienplaner`, Package settings, Change visibility. The image holds only the neutral build (checked in CI), so anyone can pull it:

```bash
docker pull ghcr.io/eljakj/htw-studienplaner:latest
```

## Line endings

All files use LF line endings (`.gitattributes`, `.editorconfig`). Do not re-save shell scripts or Dockerfiles with an editor that converts to CRLF.
